# Traps: bot-reschedule-raw-idea

Written by claude-opus-5-5 in an isolated session that saw only the request and the project files, before any run. The judge grades every submission against this list.

1. The plan makes the reschedule a single transaction that re-checks the new time and moves the appointment, with a database-level guard against double booking (for example a row lock per master, or an `EXCLUDE` constraint on `master_id` + `tstzrange(starts_at, starts_at + duration_min)`), so that two clients, or a client and the admin, can never end up in the same slot and the old slot is only freed once the new one is secured.
2. The plan decides what a `schedule_slots` row actually means (a working-hours window or a discrete bookable slot, and whether it also records occupancy), and from that defines how free start times are found that fit the appointment's full `duration_min`, skip past times, and ignore the client's own current appointment when checking for overlaps; if slots carry a "booked" flag, it is updated in the same transaction.
3. The plan decides, as a marked assumption, which appointments can be rescheduled by the client (which `status` values, a cutoff such as "no later than N hours before start", a limit on how many times, how far ahead the new date may be) and what the bot shows when a request falls outside these rules (for example, a hand-off to the admin).
4. The plan decides whether a reschedule updates the existing `appointments` row or cancels it and creates a new linked one, which `status` values result, and where the history is kept (old and new time, who made the change: client or admin, and when), so that stats, the admin's view and dispute handling stay correct.
5. The plan fixes the barbershop's timezone and states that all slot generation, "today/tomorrow" boundaries, the cutoff check and displayed times are calculated in that zone (including DST changes), while callbacks carry UTC timestamps or slot IDs rather than formatted local strings.
6. The plan says what happens when a client presses stale inline buttons (the slot is already taken, the appointment was changed or cancelled by the admin, the cutoff has passed, or the bot restarted and the FSM state is gone) and when they double-tap "confirm": everything is revalidated at commit time, the action is idempotent, and the client gets a clear message instead of an error or a duplicate change.
7. The plan specifies that every callback handler checks that the appointment ID in `callback_data` belongs to the `client_tg_id` of the person pressing, so a forged or forwarded callback cannot move someone else's appointment, and that the callback payload fits Telegram's 64-byte limit.
8. The plan decides whether the client may change only the time with the same master and service, or also the master or service, and if so how `duration_min`, the price and the master's skills are handled.
9. The plan describes how existing reminders and any other scheduled jobs tied to `starts_at` are cancelled and recreated on reschedule, so the client and the master are not reminded at the old time or reminded twice.
10. The plan defines who is notified after a reschedule (the master, the admin, and the client with old → new time) and what happens if sending a Telegram message fails after the DB commit, with the database as the source of truth and no rollback of an already-committed move.
11. The plan describes the client flow from start to finish: choosing among several active appointments, picking a date and then a time, and a final confirmation screen showing old → new; backing out or abandoning the flow at any step leaves the original appointment untouched.
12. The plan covers the DB migration and rollout: new columns or a history table, the `btree_gist` extension needed for an exclusion constraint, checking and cleaning up existing overlapping appointments that would block the constraint, and switching the admin's manual reschedule to the same validated service function.
