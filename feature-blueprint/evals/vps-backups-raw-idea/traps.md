# Traps: vps-backups-raw-idea

Written by claude-opus-5-5 in an isolated session that saw only the request and the project files, before any run. The judge grades every submission against this list.

1. The plan stores backups outside the VPS, with a different provider or at least a separate account, and uses credentials on the VPS that can only write, not delete or overwrite (append-only mode or object lock), so that a dead server, a hacked server, ransomware or a blocked hosting account cannot destroy the backups.
2. The plan backs up Postgres 16 in a consistent, version-matched way (`pg_dump -Fc` from the server's own image, or `pg_basebackup` with WAL archiving via a tool like WAL-G or pgBackRest) and explicitly forbids copying the live Docker data volume or directory as a backup.
3. The plan states a recovery point objective (RPO) and a recovery time objective (RTO) as marked assumptions, such as "at most N minutes/hours of orders and payments may be lost", and justifies nightly dumps versus continuous WAL archiving and point-in-time recovery against that number.
4. The plan includes a scheduled restore test that restores the latest DB backup into a throwaway container, runs sanity checks (table row counts, timestamp of the latest order, a sample of image files present), and records how long a full restore of about 8 GB of DB plus 40 GB of uploads actually takes.
5. The plan has written restore procedures for both a full rebuild on a fresh VPS and a partial restore of accidentally deleted products or orders. The full rebuild includes `docker-compose.yml`, `.env` secrets, nginx/TLS configs and cron, which must therefore be in the backup set. The partial restore goes into a separate database so it never overwrites orders placed after the backup.
6. The plan encrypts backups and says where the encryption key or repository password is kept off the VPS (for example with the owner, in a password manager), noting that a lost key makes every backup unusable and that the key lives on the server it is meant to protect against.
7. The plan alerts not only on failed backup jobs but also on missing ones (a dead-man's switch or freshness check), as well as on suspicious size changes, and decides which channel the owner will actually see.
8. The plan backs up the 40 GB uploads folder incrementally with deduplication (restic, borg or similar) rather than a full archive every night. It accounts for the initial upload time and bandwidth, does not need large temporary space on the VPS disk, and limits CPU and I/O impact (schedule, `nice`/`ionice`, bandwidth cap) so the live shop is not slowed down.
9. The plan handles consistency between the DB and uploads. It sets the order and timing of the two backups and keeps deleted or replaced image files long enough, so that a restored database does not reference product images that are missing from the restored uploads.
10. The plan defines a retention policy (for example daily/weekly/monthly tiers), sets up automatic pruning that the VPS credentials can run (or that runs from a separate trusted host) without weakening delete protection, and estimates the monthly storage cost for that retention.
11. The plan chooses the storage provider and location with customer personal data in mind (for a Russia-facing shop, the 152-FZ data localization requirements) and marks this choice as an assumption for the owner to confirm.
12. The plan decides whether Redis queues are backed up (RDB/AOF snapshot or deliberately not backed up). It explains what happens after a restore to queued or in-flight jobs (order emails, payment or webhook processing), whether they are lost or run twice.
