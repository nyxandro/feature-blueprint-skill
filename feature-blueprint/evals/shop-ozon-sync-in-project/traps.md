# Traps: shop-ozon-sync-in-project

Written by claude-opus-5-5 in an isolated session that saw only the request and the project files, before any run. The judge grades every submission against this list.

1. The plan decides how Ozon orders and cancellations change site stock (polling FBS postings or webhooks, without double-counting on retries), because a one-way push of site stock to Ozon still oversells the shared physical stock.
2. The plan defines how the ~1,200 Ozon products are matched to site products (is `products.sku` equal to Ozon `offer_id`, or is there a separate mapping table), how unmatched or duplicate SKUs are found and shown before the first push, and what happens when a mapped product is deleted on the site or archived on Ozon.
3. The plan covers the first launch and ongoing safety: a dry-run diff against current Ozon values, a guard that stops and asks for confirmation when a run would zero out or sharply cut the price of many products at once, a kill switch, and the rule that manual edits in the Ozon cabinet will be overwritten.
4. The plan states the exact stock number sent for each product, including clamping negative values (the `stock` column has no `CHECK >= 0`), any safety buffer, and handling of units reserved by unshipped orders.
5. The plan decides which Ozon warehouse(s) receive stock (`warehouse_id`), how stock is split if there are several FBS warehouses, and that FBO products, whose stock Ozon manages, are excluded from stock updates.
6. The plan fixes the pricing rule, marked as an assumption: Ozon price equal to the site price or a formula with markup or commission; conversion from `price_kopecks` to rubles with rounding; what is sent for `old_price` and `min_price`; refusing to send a zero price; and how Ozon promotions (акции) interact with pushed prices.
7. The plan lists every code path that changes price or stock (product create and edit, Excel or other bulk imports, order processing) and how each one triggers sync, since `updated_at` is set only on INSERT and is not maintained on UPDATE, and it adds a periodic full reconciliation to catch missed changes and manual Ozon edits.
8. The plan fixes `server/jobs/queue.js` before adding an Ozon worker, because every `registerWorker` creates a Worker on the shared `admin-jobs` queue that also takes jobs with other names and completes them silently as `undefined`, so sync jobs could be marked done without running.
9. The plan ensures retries and out-of-order jobs never push stale values: the worker reads current values from the DB at send time, collapses repeated changes to one product into one update, and runs only one Ozon sync at a time.
10. The plan handles per-item errors that Ozon returns inside a successful HTTP response: it stores per-product sync status, last sent values, time and error, and separates transient errors (retried with backoff) from permanent ones (not retried, shown to the manager).
11. The plan respects Ozon API limits (items per stock or price request, requests per minute, how often one item can be updated) with batching and 429 backoff, and estimates how long a full push of 1,200 products takes.
12. The plan defines manager-facing behavior under CLAUDE.md: stable `APP_OZON_*` codes with Russian text and a next step, one summary notification per run instead of one per failed product, sync status visible on the products page, and pausing sync with a notification when the Ozon Client-Id/Api-Key is missing, invalid or revoked, including where those credentials are stored.
