# Traps: admin-csv-import-in-project

Written by claude-opus-5-5 in an isolated session that saw only the request and the project files, before any run. The judge grades every submission against this list.

1. The plan decides what the supplier's price column means for `price_kopecks`: purchase price or retail, which markup and rounding rule applies, and how VAT is treated. It also defines exact parsing of values like "1 234,50", "1234.5 ₽", empty, zero or negative into integer kopecks with no floating-point drift, within the `CHECK (price_kopecks >= 0)` constraint.
2. The plan defines how file rows are matched to existing products, either by `products.sku` or by a separate supplier article number. It covers normalization (whitespace, case, Excel turning articles into numbers, dropping leading zeros or using scientific notation) and what happens when the same SKU appears twice in one file.
3. The plan decides what happens to products that are in the database but missing from this week's file (leave untouched, set stock to 0, or hide them), and how products from other suppliers or added manually are protected from that rule.
4. The plan specifies a dry-run preview before anything is written. The preview shows counts of new, changed, unchanged, missing and error rows plus a sample of price changes, and the manager confirms it in `ConfirmDialog`. Parsing and preview run as a `queue.js` job because they exceed 5 s, and the result arrives through `notifyUser`.
5. The plan defines guards against a wrong or corrupted file and says whether each guard blocks apply or requires an extra explicit confirmation. Examples: price changes above a threshold percentage, many prices dropping to zero, a large share of SKUs missing, a file identical to an already applied import, or a file that is clearly from another supplier.
6. The plan decides the failure semantics for applying 3000 rows: one transaction for everything, or apply valid rows and skip invalid ones. It guarantees that a worker crash or a BullMQ automatic retry cannot apply the import twice or leave it half-applied. Only rows that actually changed get a new `updated_at`, which the product list sorts by.
7. The plan provides an import history (who, when, which file, before and after values per row) and a way to roll back a mistaken import. It says what rollback does to products the import created and to products edited manually afterwards.
8. The plan states exactly which fields the import may overwrite (price, stock, name, category) and how manual edits, such as a corrected product name, survive the weekly import. It also decides whether the supplier's quantity is the shop's real `stock` or only supplier availability.
9. The plan specifies how new SKUs become products. It covers how the category is resolved against `categories` (match by name, create a new one, or leave `category_id` empty) and what happens when the name is missing. It also decides whether new items go live immediately or wait for review, given that `products` has no draft or hidden status.
10. The plan defines accepted file formats and structure: xlsx, xls or csv; encoding (Windows-1251 or UTF-8) and delimiter detection; which sheet and header row to read; column mapping by header names, saved as a per-supplier template; and file size and row limits in multer. It also says what the manager sees when required columns are not found.
11. The plan specifies row-level error reporting in the project convention, rather than one generic failure for the whole file. That means stable codes such as `APP_IMPORT_PRICE_INVALID` created via `AppError`, plain Russian text with a next step and the row number or SKU, and a downloadable error report.
12. The plan decides how concurrent activity is handled: two managers uploading at once, manual product edits or an export running during an import, and catalog changes between preview and apply (re-validate or invalidate the stale preview).
