# Масштаб и простота: какое решение выбрать

Оптимальное решение — не самое надёжное и не самое простое, а самое простое из тех, что
выполняют цели фичи на масштабе проекта сейчас и не закрывают дорогу к следующему уровню.
Переусложнение стоит дней работы, денег в месяц и новых мест для сбоев, которые некому
обслуживать. Недоусложнение стоит потерянных данных, денег и доверия — и часто его нельзя
исправить задним числом. Этот справочник — о том, как попасть между ними.

## 1. Сначала цифры

Перед выбором устройства собери масштаб — из проекта, а не из головы:

- **Данные:** сколько их сейчас и как быстро растут (размер базы и файлов, число записей).
- **Нагрузка:** пользователи, запросы, события в сутки и в пике.
- **Кто обслуживает:** команда и её время. Если это владелец и агенты, всё, что требует
  дежурного инженера или ручной работы по ночам, стоит намного дороже, чем у компании со штатом.
- **Бюджет и инфраструктура:** где работает проект, что уже оплачено, что добавит расходов.
- **Цена сбоя:** что теряет бизнес, если механизм сломается или потеряет данные: час работы,
  заказы за сутки, доверие клиентов, штраф.

Чего нет в проекте — помечай `[ДОПУЩЕНИЕ]` и вноси замер в нулевой шаг плана с пометкой
`[ЗАМЕРИТЬ]`. Боевые серверы при составлении чертежа не трогай. Владельца спрашивай, только если
от цифры переворачивается весь выбор (шаг 4 в `SKILL.md`).

## 2. Лестница решений

Лестница нужна, когда варианты различаются надёжностью, сложностью и ценой: сколько защищать,
насколько быстро, сколько движущихся частей. Чаще всего это внутренние механизмы. Если выбор не
об этом (пользовательская фича с одним разумным путём или с вариантами, которые различаются
поведением человека), лестницу не строй.

Построй 2–4 ступени — от самого простого рабочего решения до того, как это сделано у крупных
компаний. Для каждой ступени:

| | Ступень 1 | Ступень 2 | Ступень 3 |
|---|---|---|---|
| Что делаем | | | |
| От чего защищает | | | |
| От чего не защищает | | | |
| Стоит: работа | | | |
| Стоит: деньги в месяц | | | |
| Стоит: обслуживание | | | |
| Нужна, когда | | | |

Пример для резервного копирования небольшого проекта:
1. Раз в сутки копия базы и файлов в отдельное хранилище, хранение нескольких недель,
   автоматическая проверка, что из копии можно восстановиться, уведомление владельцу при сбое.
2. Плюс непрерывная запись изменений базы — восстановление на любую минуту, а не на прошлую ночь.
3. Плюс резервный сервер, который подхватывает работу сам.

Для пользовательской фичи лестница тоже бывает: обновление списка по кнопке → автоматическое
обновление раз в минуту → изменения в реальном времени.

Ступени берутся из исследования (`prior-art.md`): у каждой должен быть источник, где так делают, и
масштаб, при котором это окупается.

## 3. Как выбрать ступень

1. Возьми цели фичи в измеримых словах (сколько данных допустимо потерять, как быстро изменения
   должны доходить, сколько пользователей должно выдержать).
2. Выбери **самую низкую ступень, которая выполняет цели** на текущем масштабе и на росте, который
   виден в данных, а не в надеждах.
3. Запиши **условие перехода** на следующую ступень — измеримое: «когда база превысит N ГБ», «когда
   потеря суток данных станет недопустимой», «когда синхронизаций станет больше N в минуту». Без
   условия переход не случится вовремя или случится раньше, чем нужен.
4. Проверь, что выбранная ступень **не закрывает дорогу**: переход на следующую не потребует
   переделывать формат данных, интерфейсы или переносить всё заново.

Если цели требуют высокой ступени, а масштаб проекта маленький, — это развилка для владельца:
дорогая защита или принятый риск, в деньгах и последствиях.

## 4. Признаки переусложнения

- Новый компонент, который надо отдельно обслуживать (сервер, очередь, кластер, сервис), когда
  задачу решает уже имеющийся стек. Сначала попробуй решить имеющимся и запиши, почему не
  хватает.
- Запас под нагрузку в десятки раз больше нынешней без данных о таком росте.
- Технология, которую в команде некому чинить, когда она сломается ночью.
- Обобщение под один случай использования; настройки, которые никто не будет менять.
- «На всякий случай» без измеримого условия, при котором это понадобится.
- Практика крупной компании без её причины: у них была проблема, которой у проекта нет.

Каждая новая технология приносит обслуживание: мониторинг, обновления, знание того, как она
ломается. Скучное проверенное решение обычно выигрывает у идеального нового — у него известны
и возможности, и способы сломаться.

## 5. Где экономить нельзя

Простое решение не означает хрупкое. Не упрощай:

- **Необратимое:** потеря данных, деньги, удаление, отправка людям.
- **Безопасность и доступы:** секреты, права, персональные данные, требования закона.
- **То, что дёшево сейчас и дорого потом:** формат и идентификаторы данных, ключи защиты от
  двойного выполнения, история изменений, возможность отката. Переделка после запуска означает
  перенос живых данных.
- **Сигнал о сбое:** механизм, который ломается молча, хуже механизма, которого нет, — на него
  рассчитывают.

## 6. Что записать в документ

В разделе «Варианты и масштаб»: цифры масштаба с источником; если строил лестницу — её таблицу,
выбранную ступень с причиной, условие перехода на следующую и чем платим за простоту. Отвергнутые ступени
не удаляй — они отвечают на вопрос «почему не сделать надёжнее» и «почему не сделать проще».
